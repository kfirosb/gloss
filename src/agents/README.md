# Versioned local coding adapters

These adapters attach to an existing exact coding session; they never start, resume, fork, interrupt, or terminate it. They are experimental integrations with version-sensitive local files. The tested baseline and current exact allowlist are **Claude Code 2.1.273** and **Codex CLI 0.154.0**. Newer versions require a new protocol verification and parser review; an unverified version fails closed.

`createClaudeAdapter(options)` and `createCodexAdapter(options)` implement the core `AgentAdapter` contract. Both accept `runner`, `pollMs`, `pageSize`, an abortable `clock.sleep`, and an optional trusted server `observeLive(target)` probe. Never populate this probe or credentials from browser-supplied claims.

Claude uses `configDir` (default `CLAUDE_CONFIG_DIR` or `~/.claude`) for session registry metadata. Resolve server `transcriptPath(target)` from exact trusted registry identity; SessionStart hooks are historical research, not recommended setup. The fallback checks only filenames `<session UUID>.jsonl` in project directories, rejecting ambiguous candidates; it never opens unrelated transcripts. Attachment verifies the first bounded identity-bearing record and earlier explicit session IDs. An optional server `credentials(target)` supplies the exact coding child's socket token; tokens never enter browser events or persistence. On macOS/Linux, the adapter can send to the verified live session socket without a token. Other platforms require credentials; missing connections fail without launching a separate Claude process. Superset is not required. Socket writes remain **unconfirmed** until native peer consumption is correlated using `origin.msg_id` or the per-request Gloss marker preserved in newer Claude transcripts. The marker and known permission wrapper are removed from displayed peer text. Native permission checks remain in force. Default liveness detection currently supports macOS; Linux requires a trusted `observeLive` implementation.

Codex uses `codexHome` (default `CODEX_HOME` or `~/.codex`) and `databasePath` (default `state_5.sqlite`). Queries read metadata only and verify the exact project/thread plus native session header before reading history. Only completed `UserMessage`/`AgentMessage` events are exposed, excluding raw model context and tools. Sending also gates the installed `codex --version`, then invokes shell-free `queue --thread <UUID> --message=<exact reviewed text>`. Exit zero is insufficient: only `Queued message <UUID> for thread <exact UUID>.` establishes **queued**, never **sent**.

Default liveness is macOS-only: read-only `lsof -Fpcfn` (one batched call for every Claude socket, answers reused for 3 s per PID/socket/version, skipped when `kill(pid, 0)` reports the process gone) must observe the named `claude` or exact supported version (`2.1.273`) process/PID on its inbox socket or `codex` on the exact native writer-lock file. An existing lock file alone is insufficient. This observes an open writer file, not OS advisory-lock state; stronger liveness or other platforms need an independently verified probe. Claude idle is explicitly whitelisted; recognized approval values are blocked, unknown states stay working. Codex requires both a live writer and a latest observed completed/aborted turn. Native approval prompts lack rollout state, so a started turn remains working and app sending is blocked. Both advertise `sendWhileBusy:false`.

The reader polls at most 1 MiB per iteration, caches at most 10,000 message signatures, uses the earliest byte-position revision in each uninterrupted same-content run within the bounded replay/index window, and suppresses identical repeated messages. History normalizes its bounded read window forward before choosing latest records, so duplicate physical rows do not invent revisions; X → Y → X still advances the revision. An explicit replay/cache gap marks where earlier canonical positions may no longer be known. Initial live replay is bounded to the tail with an explicit gap; older history is paginated directly from the exact file (at most eight 1 MiB scans per request, possibly an empty page with a continuation). Pagination cursors belong to one attachment. Inode changes, truncation, checkpoint rewrites, malformed records, and conflicting IDs invalidate the attachment and emit a gap. This assumes native append-only transcript behavior; it is not a cryptographic integrity monitor for arbitrary edits elsewhere in a file. Transient registry/liveness lookup failures preserve already parsed messages and delivery receipts while reporting disconnected; status can recover on a later poll. Detach aborts watchers only. It never signals the original coding process.

Tests use sanitized native fixtures, temporary real transcripts/SQLite metadata, a real Unix socket, and a real child process emulating the captured queue output. The child test proves argv/receipt handling, not account-backed delivery. Controller-owned disposable CLI smoke results are recorded separately in the task report; no adapter should be called generally verified across versions/platforms.

## Codex shared app-server daemon: when a thread is open (Codex CLI 0.162.1)

Codex 0.162 runs conversations inside a shared local app-server daemon (`~/.codex/packages/app-server-daemon/.../codex app-server`); the terminal UI is only a client. After the client exits (End session, `/exit`, crash) the daemon keeps the thread loaded and keeps holding `thread-writer-locks/<thread>.lock`, so writer-lock ownership alone no longer means anything can process a queued message. `src/agents/codex/liveness.ts` therefore treats a locked thread as **open** only in these cases, in precedence order:

1. **Launched by Gloss** (the trusted server `launched(sessionRef)` hook, fed from launch records): open while the launch's tmux session runs; the launcher's watch moves a launch whose tmux session is gone to ended within a few seconds. After the launch ended, only an exact signal from (2) or `codex resume <id>` reopens the thread; the folder heuristic does not.
2. **Lock held by a terminal client itself** (lock owner is a `codex` process whose command line is not `app-server`): open.
3. **Lock held by the daemon**: open only with an attached terminal client. Signals, from one `ps -axww -o pid=,etime=,ucomm=,args=` plus, only when the daemon holds a lock, one `lsof -a -d cwd` over candidate client PIDs: a live `codex resume <thread UUID>` client names the thread exactly; otherwise a live client (no subcommand, or a prompt) whose working directory (or `-C/--cd`) is the thread's folder and that started at or before the thread's creation time (2 s skew) claims the newest such unclaimed thread. Each client claims at most one thread, because it shows one conversation at a time.

Everything else is **closed**: discovery omits it (so its tab moves to history and it can be removed), status reports `disconnected`, and sending fails before `codex queue` runs with the reason `CODEX_CLOSED_REASON` rather than queueing a message nothing would process. A failed process probe makes discovery incomplete (rows are kept, not closed) and makes status report disconnected. One probe round (writer `lsof`, `ps`, and the `cwd` `lsof` when needed) is shared by discovery and every connection of an adapter for 3 s after it finished; an incomplete round is not reused, and every send probes afresh.

Known limits: the daemon offers no read-only, cheap query of attached clients (`codex agents` is an interactive browser), so attachment is inferred. A client that switched threads (`/new`, `/resume` picker, `codex resume` without an ID, `codex resume --last`) or a client attached through `--remote`, the Desktop app or an IDE is not recognized for an older daemon-held thread, which then reads as closed (unavailable for sending) — the safe direction. Two clients in the same folder may be paired with the wrong threads among their own. Command lines are split on spaces, so `-C` paths containing spaces are not resolved. macOS only, like the other liveness probes.

New Codex launches pass the disclosed setup prompt `Reply with READY only. Do not run commands.` (`CODEX_SETUP_PROMPT`) as the positional `[PROMPT]` last, after the user's extra arguments and a `--` separator, so Codex creates the thread immediately (one model request), a value-taking extra option cannot consume it, and a first message starting with `-` is not read as an option. Extra arguments that name a subcommand (for example `resume`) are incompatible with this prompt.

## Experimental Claude channels (2026-10-07)

Native Claude 2.1.293 was tested on macOS in disposable ordinary and bypass sessions using the assembled application. Channel setup is explicit: run the generated new-session or exact-session resume command yourself and accept native development-channel consent. Existing user sessions are never automatically restarted or replayed. Normal commands preserve other MCP/settings; isolated probe flags are not product defaults. Peer sending remains a separate explicit route, never a silent channel fallback. Native ordinary approval stays native; there is no permission relay.

Channel ledgers use verified DELETE journal with synchronous FULL and a bounded busy timeout on every connection. Busy legacy WAL conversion fails closed. Node 24.4.1 bundles SQLite 3.50.3, affected by the official WAL-reset bug; this correction avoids WAL only for channel ledgers. Existing panelstate.db WAL is NOT changed or certified safe by it. A separate reviewed risk ruling/remediation is required before release; no global Node upgrade is performed.

See `scripts/probes/README.md` and `docs/superpowers/research/2026-10-07-claude-channel-integration.md` for exact isolation, evidence and remaining review gates. Historical adapter baselines above are not a blanket compatibility guarantee for newer native versions.

## Claude activity (2026-10-18)

`parseClaudeActivity` in `src/agents/claude/activity.ts` turns `tool_use` and `tool_result` blocks of each transcript record into activity events (tool calls, results, subagent launches and background task outputs); it is pure and ignores malformed input. Sidechain records in the main transcript are skipped; a subagent's own records are read only from its file. A synchronous subagent's report is its `Agent` tool result; an async one's (Claude 2.1.302 launches subagents async) arrives as a peer hand-back record and is read only from the harness's structured `origin` fields (`handback`, `senderTaskId`, `handbackReportText`), never from the framed message text. On attach, `Transcript.lookbackActivity` in `src/agents/shared.ts` (enabled by the reader's `activityLookback` option, which only the Claude adapter sets) scans at most 8 windows of 1 MiB before the 1 MiB live tail so tasks still running are found; anything older is reported as a `gap`, and a failed lookback never stops the live tail. A subagent is paired with its parent call through `<transcript dir>/<session UUID>/subagents/agent-<id>.meta.json`, whose `toolUseId` names the call; `agent-<id>.jsonl` is then streamed only while a client has it open (`GET /api/sessions/:id/activity/subagents/:taskId/events`). The page keeps at most `ACTIVITY_STREAM_LIMIT = 3` activity streams (subagent streams and output tails) open at once, by priority: user-expanded > running subagent card > background strip tail. A claim preempts only a less important holder, otherwise it waits; a holder keeps its slot until it finishes or is collapsed (`StreamSlots` in `src/ui/use-activity-streams.ts`). A background command's output path comes from the transcript, so it is trusted only if, after resolving, it ends in exactly `claude-<uid>/<project dir>/<session UUID>/tasks/<id>.output` (every part a single path segment), is not a symlink, is a regular file and is owned by the current user (`validateBackgroundOutputPath` in `src/agents/claude/background-output.ts`); `GET .../activity/tasks/:taskId/output[?end=n]` then serves bounded 64 KiB windows opened with `O_NOFOLLOW`. Codex has no activity source yet. As of 2026-10-19 the Activity view shows only active agents (finished ones move to History) and nothing in it is translated; the server contract is unchanged except the removed translation action.

## Live panel source sink

`AdapterOptions.sourceSink` is an optional host bridge used by a local panel process. The transcript connection sends only complete assistant messages, with the exact session ID, stable native message ID, revision sequence, and cursor. User messages, partial assistant records, tool records, internal context, and terminal noise are never sent to the sink. Sink failures are retained for retry on the next poll; reconnecting replays bounded native history and the panel endpoint deduplicates retries.

`createHttpSourceSink` in `src/agents/source-sink.ts` posts these records to `/api/source/messages` using the loopback capability. The sink is opt-in so the normal in-process workflow remains available.
